# Java en 2026: el lenguaje principal del curso

> Java es **el lenguaje de este módulo**. Esta página te pone al día de dónde está Java hoy: versiones, qué JDK usaremos y qué características modernas vas a usar de verdad. Olvida el Java "viejo" de los tutoriales de 2015: el Java de 2026 es otro lenguaje.

## 1. Versiones: cadencia y LTS

Desde 2018, Java publica **una versión cada 6 meses** (marzo y septiembre). Cada cierto tiempo, una de ellas se marca como **LTS** (*Long-Term Support*): soporte extendido durante años, la que usan las empresas en producción.

| Versión | Salida | Tipo | Estado en 2026 |
|---------|--------|------|-----------------|
| Java 17 | 2021 | LTS | Aún muy presente en empresas |
| Java 21 | 2023 | LTS | Muy extendida (virtual threads) |
| **Java 25** | Sept 2025 | **LTS actual** | **La que usaremos en el curso** |
| Java 26 | Marzo 2026 | Intermedia | La última publicada (26.0.2); soporte 6 meses |
| Java 27 | Sept 2026 | Intermedia | Prevista |

**En este curso: JDK 25 (LTS).** Es lo que te pedirán en las empresas: la LTS vigente. Instálala de [Adoptium/Temurin](https://adoptium.net) (gratuita, open source) o del [propio Oracle](https://www.oracle.com/java/technologies/downloads/).

> Regla profesional: **en producción, LTS**. Las versiones intermedias (26, 27) sirven para probar lo que viene, no para desplegar.

## 2. El Java moderno que SÍ vamos a usar

Estas características ya son estándar y las usaremos desde la UT2. Si vienes del Java clásico de 1.º, esto te va a gustar:

### `var` — inferencia de tipos (Java 10+)
```java
var lista = new ArrayList<Producto>();   // el compilador deduce el tipo
var precio = 19.99;
```

### Records — clases de datos en una línea (Java 16+)
Adiós a los 50 renglones de getters, `equals` y `toString`:
```java
public record Producto(Long id, String nombre, double precio) {}

var p = new Producto(1L, "Patinete", 120.0);
System.out.println(p.nombre());   // getters automáticos
```
Los usaremos constantemente como **DTOs** en las APIs REST.

### Text blocks — cadenas multilínea (Java 15+)
```java
String json = """
    {
      "nombre": "Ana",
      "rol": "admin"
    }
    """;
```

### Switch con pattern matching (Java 21+)
```java
String etiqueta = switch (objeto) {
    case Producto p when p.precio() > 100 -> "Caro: " + p.nombre();
    case Producto p -> "Barato: " + p.nombre();
    case null -> "Nada";
    default -> "Desconocido";
};
```

### Virtual threads — concurrencia masiva (Java 21+)
El cambio más importante para **servidores**: hilos ultraligeros que permiten atender miles de peticiones simultáneas sin la complejidad de la programación reactiva.
```java
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    executor.submit(() -> atenderPeticion());   // miles de estos, sin miedo
}
```
Spring Boot los activa con una línea de configuración. Lo veremos en el bloque de servicios.

### Sealed classes e interfaces (Java 17+)
Jerarquías cerradas: solo pueden heredar quienes tú digas. Combinadas con `switch` dan modelado de dominios muy expresivo.

## 3. El ecosistema que acompaña al lenguaje

- **Spring Boot** (usaremos la última estable, sobre JDK 25): el framework de backend más demandado del mercado. Arranque embebido, inyección de dependencias, Spring Data, Spring Security.
- **Gradle / Maven:** gestión de dependencias y construcción del proyecto.
- **JUnit 5 + Mockito:** testing (lo usaremos desde el principio).
- **Docker:** empaquetado y despliegue de nuestras apps.
- **La JVM como plataforma:** lo que aprendas vale también para **Kotlin** (mismo ecosistema) y se transfiere con facilidad a C#.

## 4. ¿Por qué Java y no otro?

Respuesta honesta, con sus contras:

| A favor | En contra |
|---------|-----------|
| Estándar de la industria "seria": banca, seguros, administración, grandes plataformas | Más verboso que Python o JS (aunque records y `var` lo han aliviado mucho) |
| El ecosistema backend más maduro (Spring) | Arranque de JVM más pesado que un binario nativo (Go/Rust) |
| Portabilidad real: bytecode sobre la JVM | La fama de "antiguo" (injusta desde Java 17+) |
| Con virtual threads, rendimiento de servidor excelente | — |
| **Empleo**: es de lo más solicitado en ofertas de backend en España | — |

## Ejercicios (con solución)

### Ejercicio 1 — LTS

¿Qué es una versión LTS y por qué el módulo usa la 25 y no la última que exista?

??? success "Solución"

    **LTS** es *Long Term Support*: una versión con soporte y parches de seguridad durante años, no seis meses.

    Java saca una versión cada seis meses, pero **solo algunas son LTS**: la 8, la 11, la 17, la 21 y la 25.

    Las intermedias sirven para probar novedades, y dejan de recibir parches en cuanto sale la siguiente. Nadie pone eso en producción.

    Por qué la 25 en el módulo:

    1. Es **la LTS actual**, con soporte por delante.
    2. Es la que te vas a encontrar en las empresas que se mantienen al día.
    3. Trae lo moderno —records, `switch` con patrones, hilos virtuales— sin ser experimental.

    El detalle práctico: el `spring-boot-starter-parent` **también** tiene que admitirla. Spring Boot 3.5 sí; la 3.4 solo llega a Java 23.

### Ejercicio 2 — `var`, bien y mal

Di si cada uso es correcto y por qué.

```java
var lista = new ArrayList<String>();
var x = servicio.buscar();
var i = 0;
var total = calcularTotal(pedido);
```

??? success "Solución"

    | | ¿Bien? | Por qué |
    |---|:-:|---|
    | `var lista = new ArrayList<String>();` | **Sí** | El tipo está a la derecha. Repetirlo a la izquierda es ruido |
    | `var x = servicio.buscar();` | **No** | Ni el nombre ni la derecha dicen qué es. ¿Una lista? ¿Un `Optional`? |
    | `var i = 0;` | **Sí** | Obvio, y en un bucle es lo normal |
    | `var total = calcularTotal(pedido);` | **Depende** | Si devuelve `BigDecimal`, bien: el nombre lo sugiere. Si devuelve `double`, **peor**, porque esconde justo lo que hay que ver |

    **La regla:** `var` cuando el tipo se lee en la misma línea o es evidente. Si al leerla tienes que ir a mirar la firma del método, escribe el tipo.

    Y una cosa que no cambia: **`var` no es dinámico**. El tipo se decide al compilar y luego es fijo. `var i = 0; i = "hola";` no compila.

### Ejercicio 3 — Records

Escribe con un `record` esta clase, y di qué te llevas gratis.

```java
public class Punto {
    private final int x;
    private final int y;
    public Punto(int x, int y) { this.x = x; this.y = y; }
    public int getX() { return x; }
    public int getY() { return y; }
    // equals, hashCode y toString a mano...
}
```

??? success "Solución"

    ```java
    public record Punto(int x, int y) {}
    ```

    Gratis vienen:

    - **El constructor** `Punto(int, int)`.
    - **Los accesores** `x()` e `y()`. Ojo: se llaman así, no `getX()`.
    - **`equals` y `hashCode`** por valor. Dos puntos con las mismas coordenadas son iguales, que es lo que quieres y lo que casi nadie escribía bien a mano.
    - **`toString`**: `Punto[x=3, y=4]`.
    - **Inmutabilidad**: los campos son finales.

    Se le pueden añadir métodos y validar en el constructor compacto:

    ```java
    public record Punto(int x, int y) {
        public Punto {
            if (x < 0 || y < 0) throw new IllegalArgumentException("Sin negativos");
        }
        public double distanciaAlOrigen() { return Math.hypot(x, y); }
    }
    ```

    **Dónde NO valen**, y se pregunta: como entidad JPA y como objeto de formulario. Las dos necesitan constructor vacío y *setters*.

### Ejercicio 4 — Hilos virtuales

¿Qué problema resuelven y por qué importan en un módulo de servidor?

??? success "Solución"

    Resuelven que **un hilo del sistema operativo es caro**: cada uno reserva alrededor de 1 MB de pila. Con 200 hilos ya vas justo, así que un servidor tradicional los reparte con mucho cuidado.

    El problema es qué hacen esos hilos la mayor parte del tiempo: **esperar**. Esperan a la base de datos, esperan a una API ajena. Un recurso caro, parado.

    Un **hilo virtual** lo gestiona la JVM, no el sistema, y cuesta unos cientos de bytes. Puedes tener **cientos de miles**. Cuando uno se bloquea esperando, la JVM lo aparta y aprovecha el hilo real para otro.

    ```java
    // Un hilo virtual por tarea, sin miedo
    try (var ejecutor = Executors.newVirtualThreadPerTaskExecutor()) {
        for (var codigo : municipios) {
            ejecutor.submit(() -> aemet.deMunicipio(codigo));
        }
    }
    ```

    En Spring Boot se activan con una línea:

    ```yaml
    spring.threads.virtual.enabled: true
    ```

    **Por qué importa aquí:** en la UT9 vas a llamar a varias APIs a la vez. Antes eso obligaba a programación reactiva, con un modelo mental mucho más difícil. Ahora se escribe el código bloqueante de siempre, que se lee de arriba abajo, y escala igual.

### Ejercicio 5 — `switch` con patrones

Reescribe esto con el `switch` moderno.

```java
if (figura instanceof Circulo c) {
    return Math.PI * c.radio() * c.radio();
} else if (figura instanceof Rectangulo r) {
    return r.ancho() * r.alto();
} else {
    throw new IllegalArgumentException("Figura desconocida");
}
```

??? success "Solución"

    ```java
    return switch (figura) {
        case Circulo c     -> Math.PI * c.radio() * c.radio();
        case Rectangulo r  -> r.ancho() * r.alto();
        default            -> throw new IllegalArgumentException("Figura desconocida");
    };
    ```

    Y si `Figura` es **sellada**, el `default` sobra:

    ```java
    public sealed interface Figura permits Circulo, Rectangulo {}

    return switch (figura) {
        case Circulo c    -> Math.PI * c.radio() * c.radio();
        case Rectangulo r -> r.ancho() * r.alto();
    };
    ```

    Aquí está lo bueno: al ser sellada, el compilador **sabe** que solo hay dos casos. Y el día que añadas `Triangulo`, **el código deja de compilar** hasta que lo trates. Con la cadena de `if` te habrías enterado en producción, con una excepción.

    Se pueden añadir condiciones:

    ```java
    case Rectangulo r when r.ancho() == r.alto() -> "Es un cuadrado";
    ```

### Ejercicio 6 — Java y no otro

¿Por qué Java para el servidor y no otro lenguaje? Da dos argumentos y un contraargumento honesto.

??? success "Solución"

    **A favor**

    1. **Es lo que hay en el mercado que te va a contratar.** Banca, seguros, administración y grandes empresas van con Java, y ahí el código vive quince años. Ese es el argumento que importa cuando salgas.
    2. **El ecosistema está resuelto.** Spring Boot, JPA, JUnit, Maven: para cualquier problema de servidor hay una solución madura, documentada y con gente que la conoce.

    **En contra, y es cierto**

    Java es **más ceremonioso** que Python o JavaScript. Un servicio pequeño se levanta antes con FastAPI o con Express. Y arrancar una JVM tarda más y consume más memoria que un proceso de Go.

    Lo que compensa la balanza: **esa ceremonia se paga una vez y se cobra durante años**. Los tipos, el compilador y las herramientas cazan en el IDE lo que en un lenguaje dinámico aparece en producción. En un proyecto de 20 ficheros da igual; en uno de 2.000, es la diferencia entre poder tocarlo y no atreverse.
