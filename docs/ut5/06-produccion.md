# De H2 a producción

> Todo lo anterior funciona con `ddl-auto: update` y H2 en memoria. Eso está muy bien para aprender y **no se puede llevar a producción**. Este tema es el puente.

## 1. Por qué `ddl-auto: update` no vale

Hibernate mira tus entidades, compara con las tablas y las modifica. Suena perfecto y tiene tres problemas serios:

| Problema | Qué pasa |
|---|---|
| **No borra ni renombra** | Quitas un campo de la entidad y la columna se queda ahí para siempre |
| **No sabe migrar datos** | Divides `nombre` en `nombre` y `apellidos` y tus datos no se reparten solos |
| **No es reproducible** | El esquema depende del orden en que se ejecutaron los cambios; dos entornos acaban distintos |

Y el que asusta de verdad: `ddl-auto: create-drop` **borra la base de datos entera al arrancar**. Un despiste en el perfil de producción y no hay vuelta.

| Valor | Qué hace | Dónde |
|---|---|---|
| `create-drop` | Crea al arrancar, borra al parar | Tests |
| `update` | Intenta ajustar | Desarrollo, y con cuidado |
| `validate` | Comprueba que el esquema cuadra y **no toca nada** | **Producción** |
| `none` | Ni mira | Producción con migraciones |

## 2. Flyway: el esquema como código

La solución profesional es tratar el esquema igual que el código: **ficheros versionados en Git**.

```xml title="pom.xml"
<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-core</artifactId>
</dependency>
```

``` { .text .sinajuste }
src/main/resources/db/migration/
├── V1__esquema_inicial.sql
├── V2__anadir_indice_categoria.sql
├── V3__tabla_pedidos_y_lineas.sql
└── V4__producto_precio_a_decimal.sql
```

```sql title="src/main/resources/db/migration/V1__esquema_inicial.sql"
CREATE TABLE productos (
    id         BIGINT       GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    nombre     VARCHAR(100) NOT NULL,
    categoria  VARCHAR(40)  NOT NULL,
    precio     DECIMAL(10,2) NOT NULL,
    stock      INTEGER      NOT NULL DEFAULT 0,
    creado_en  TIMESTAMP    NOT NULL,
    version    BIGINT       NOT NULL DEFAULT 0,
    CONSTRAINT uk_producto_nombre UNIQUE (nombre)
);

CREATE INDEX idx_producto_categoria ON productos (categoria);
```

```yaml title="src/main/resources/application.yml"
spring:
  jpa:
    hibernate:
      ddl-auto: validate      # Hibernate ya no toca el esquema; solo comprueba
  flyway:
    enabled: true
    baseline-on-migrate: true
```

Flyway lleva la cuenta en una tabla `flyway_schema_history`: al arrancar aplica lo que falte, **en orden y una sola vez**. Cualquier entorno —tu portátil, el del compañero, producción— acaba con exactamente el mismo esquema.

!!! danger "Una migración aplicada no se edita jamás"
    Flyway guarda un *checksum* de cada fichero. Si cambias una migración ya aplicada, falla al arrancar con `Migration checksum mismatch`. Y hace bien: en producción esa migración ya corrió, y editarla dejaría los entornos distintos. **Se corrige con una migración nueva**, nunca tocando la anterior.

## 3. PostgreSQL con Docker

```yaml title="compose.yaml"
services:
  db:
    image: postgres:17-alpine
    environment:
      POSTGRES_DB: tienda
      POSTGRES_USER: tienda
      POSTGRES_PASSWORD: ${DB_PASSWORD:-desarrollo}
    ports: ["5432:5432"]
    volumes: ["datos-db:/var/lib/postgresql/data"]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U tienda"]
      interval: 5s
volumes:
  datos-db:
```

```bash
docker compose up -d
docker compose logs -f db
```

Ese `volumes` es lo que hace que los datos **sobrevivan** a `docker compose down`. Sin él, cada reinicio empieza de cero.

### La misma aplicación, dos bases de datos

Estas dos configuraciones conviven en el mismo proyecto: una por perfil. Compáralas línea a línea, porque **cada diferencia tiene un motivo**.

=== "H2 (desarrollo)"

    ``` yaml title="src/main/resources/application-dev.yml"
    spring:
      datasource:
        url: jdbc:h2:mem:tienda;DB_CLOSE_DELAY=-1
        username: sa
        password:
      h2:
        console:
          enabled: true          # http://localhost:8080/h2-console
      jpa:
        hibernate:
          ddl-auto: create-drop
        show-sql: true
    ```

    | | |
    |---|---|
    | Arranca en | ~0 s, va dentro del `.jar` |
    | Los datos | se pierden al parar la aplicación |
    | Esquema | lo inventa Hibernate al arrancar |
    | Sirve para | aprender, iterar rápido, tests |
    | **No sirve para** | **producción, ni de lejos** |

=== "PostgreSQL (producción)"

    ``` { .yaml .annotate title="src/main/resources/application-prod.yml" hl_lines="5 8" }
    spring:
      datasource:
        url: jdbc:postgresql://localhost:5432/tienda
        username: ${DB_USER}
        password: ${DB_PASSWORD}    # (1)!
      jpa:
        hibernate:
          ddl-auto: validate        # (2)!
        properties:
          hibernate.jdbc.batch_size: 50
      flyway:
        enabled: true               # (3)!
    ```

    1.  **Nunca la contraseña en el fichero.** `${DB_PASSWORD}` la lee de una variable de entorno; el fichero va a Git, la variable no.
    2.  **`validate`, no `update`.** Hibernate comprueba que el esquema coincide con las entidades y **falla al arrancar** si no. En producción, arrancar con el esquema equivocado es peor que no arrancar.
    3.  Con Flyway activo, **el esquema lo definen las migraciones**, no Hibernate. `validate` solo verifica que ambos coinciden.

    | | |
    |---|---|
    | Arranca en | segundos, proceso aparte (Docker) |
    | Los datos | persisten en un volumen |
    | Esquema | lo controla **Flyway**, versionado en Git |
    | Sirve para | producción, y para tests con Testcontainers |
    | Cuesta | tener Docker levantado |

!!! danger "Lo que se rompe al pasar de H2 a PostgreSQL"
    H2 es tolerante; PostgreSQL no. Lo que funcionaba y deja de funcionar:

    - Los **nombres en mayúsculas** se comportan distinto (PostgreSQL los pasa a minúscula salvo que los entrecomilles).
    - **`GenerationType.IDENTITY` conviene cambiarlo a `SEQUENCE`**: en PostgreSQL es la estrategia nativa y permite insertar por lotes.
    - El **SQL nativo** que escribiste con funciones propias de H2 sencillamente no existe.

    Por eso probar contra el mismo motor que producción no es un lujo. Ese es el argumento de Testcontainers, dos apartados más abajo.

## 4. Probar el acceso a datos

**`@DataJpaTest`** levanta solo la capa de persistencia, con base de datos en memoria y **rollback automático** al terminar cada test:

``` { .java .numerado }
@DataJpaTest
class ProductoRepositorioTest {

    @Autowired ProductoRepositorio repositorio;
    @Autowired TestEntityManager em;

    @Test
    void buscaPorCategoria() {
        em.persist(new Producto("Casco", "seguridad", new BigDecimal("49.99"), 10));
        em.persist(new Producto("Bici",  "movilidad", new BigDecimal("899.00"), 2));
        em.flush();

        assertThat(repositorio.findByCategoria("seguridad"))
                .hasSize(1)
                .extracting(Producto::getNombre).containsExactly("Casco");
    }

    @Test
    void elNombreEsUnico() {
        em.persist(new Producto("Casco", "seguridad", new BigDecimal("49.99"), 10));
        em.flush();

        assertThatThrownBy(() -> {
            em.persist(new Producto("Casco", "movilidad", new BigDecimal("10.00"), 1));
            em.flush();
        }).isInstanceOf(PersistenceException.class);
    }
}
```

Ese segundo test es importante: **comprueba que la restricción existe de verdad**, no que tu servicio la comprueba.

**Testcontainers** cuando quieras la base de datos real:

```java
@SpringBootTest
@Testcontainers
class PedidoIntegracionTest {

    @Container
    @ServiceConnection
    static PostgreSQLContainer<?> db = new PostgreSQLContainer<>("postgres:17-alpine");
    // @ServiceConnection configura la URL solo: no hace falta @DynamicPropertySource
}
```

Levanta un PostgreSQL de verdad en Docker durante los tests. Es lento comparado con H2, así que se reserva para los flujos críticos, pero es la única forma de detectar lo que solo falla en el motor real.

## 5. Datos de prueba sin ensuciar producción

```java
@Component
@Profile("dev")                       // solo en desarrollo
public class Semilla implements CommandLineRunner {

    private final ProductoRepositorio repositorio;

    @Override
    public void run(String... args) {
        if (repositorio.count() > 0) return;  // idempotente: no duplica al reiniciar
        repositorio.saveAll(List.of(
                new Producto("Patinete", "movilidad", new BigDecimal("299.00"), 4),
                new Producto("Casco",    "seguridad", new BigDecimal("35.50"), 20)));
    }
}
```

El `if (count() > 0) return` es lo que hace que puedas reiniciar sin acumular basura.

## 6. La lista de producción

- [ ] `ddl-auto: validate` o `none`. **Nunca** `update` ni `create-drop`
- [ ] Migraciones con Flyway, versionadas en Git
- [ ] Credenciales en variables de entorno
- [ ] *Pool* de conexiones dimensionado (`spring.datasource.hikari.maximum-pool-size`)
- [ ] Índices en las columnas por las que se filtra y se ordena
- [ ] `@Version` en las entidades que se editan concurrentemente
- [ ] Copias de seguridad **con restauración probada**
- [ ] `show-sql: false` en producción: llena el disco y filtra datos
- [ ] Sin `spring.jpa.open-in-view` (viene activo por defecto: desactívalo)

!!! tip "El punto que casi nadie hace"
    **Restauración probada.** Una copia de seguridad que nunca se ha restaurado no es una copia de seguridad: es un fichero. Prueba el proceso completo al menos una vez, cronometrando cuánto tarda.

## Ejercicios (con solución)

### Ejercicio 1 — El valor de `ddl-auto`
Para desarrollo, tests, preproducción y producción, ¿cuál pones en cada uno y por qué?

??? success "Solución"

    <b>Tests:</b> <code>create-drop</code>, para empezar limpio en cada ejecución. <b>Desarrollo:</b> <code>update</code> al principio, y <code>validate</code> + Flyway en cuanto el proyecto va en serio. <b>Preproducción y producción:</b> <code>validate</code>, para que la aplicación no arranque si el esquema no cuadra con las entidades — un fallo temprano y ruidoso es mejor que una columna que falta descubierta a mitad de mañana.<br>
    <code>none</code> también vale en producción si prefieres no pagar ni la comprobación.


### Ejercicio 2 — La migración editada
Un compañero corrige un error en `V3` que ya está en producción. ¿Qué pasa y cómo se arregla?

??? success "Solución"

    Al arrancar, Flyway compara el <i>checksum</i> del fichero con el guardado y falla: <code>Migration checksum mismatch</code>. Y hace bien, porque en producción esa migración <b>ya se ejecutó</b> y editarla no cambia nada allí; solo conseguiría que los entornos divergieran.<br>
    Se arregla con una <b>V4 nueva</b> que corrija lo que estaba mal. Nunca tocando la V3. Si el error es grave y aún no salió de local, se puede borrar la fila del historial y volver a aplicar, pero eso solo en tu máquina.


### Ejercicio 3 — H2 en tests o Testcontainers
¿Cuándo compensa cada uno?

??? success "Solución"

    <b>H2</b> para el grueso: <code>@DataJpaTest</code> arranca en milisegundos y permite tener cientos de tests que se ejecutan en cada compilación. <b>Testcontainers</b> para los flujos críticos y para todo lo que dependa del motor real: SQL nativo, funciones específicas, tipos como <code>jsonb</code>, comportamiento de bloqueos.<br>
    El riesgo de usar solo H2 es real: pasan los tests y falla en producción porque PostgreSQL es más estricto. La pirámide razonable: muchos con H2, unos pocos con Testcontainers.


### Ejercicio 4 — `open-in-view`
Spring Boot activa `spring.jpa.open-in-view` por defecto. ¿Qué hace y por qué desactivarlo?

??? success "Solución"

    Mantiene la sesión de Hibernate abierta <b>durante toda la petición</b>, incluida la serialización de la respuesta. Eso hace que las relaciones perezosas se carguen «solas» al renderizar el JSON y evita la <code>LazyInitializationException</code>… disparando consultas <b>desde la capa web</b>, fuera de tu control y de cualquier transacción.<br>
    Es decir: esconde el problema N+1 en vez de resolverlo, y mantiene una conexión ocupada más tiempo del necesario. Se desactiva con <code>spring.jpa.open-in-view: false</code> y se resuelve bien: <code>JOIN FETCH</code> y DTO.


### Ejercicio 5 — Plan de despliegue
Redacta el plan para poner la TiendaAPI en producción con base de datos: entornos, esquema, credenciales, copias y qué comprobar tras desplegar.

??? success "Solución"

    <b>Entornos:</b> misma imagen, distinta configuración por perfil; PostgreSQL en los tres, nunca H2 en preproducción.<br>
    <b>Esquema:</b> Flyway con las migraciones en Git y <code>ddl-auto: validate</code>; se aplican al arrancar, y el despliegue falla si una migración falla.<br>
    <b>Credenciales:</b> variables de entorno o un gestor de secretos; jamás en el repositorio, y rotables sin recompilar.<br>
    <b>Copias:</b> automáticas diarias, retención definida y —lo que casi nadie hace— <b>restauración probada</b> al menos una vez, cronometrada.<br>
    <b>Tras desplegar:</b> <code>/actuator/health</code> en verde, una operación de lectura y una de escritura reales, revisar el log de Flyway y vigilar la tasa de 5xx la primera hora.<br>
    <b>Y antes de nada:</b> ensayar la migración sobre una <b>copia de los datos de producción</b>. Una migración que tarda 40 minutos sobre 20 millones de filas es un problema que quieres descubrir el jueves por la tarde, no el lunes a las nueve.
